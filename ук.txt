## 1. Что такое JMX и MBean — вступление

**Что говорить:**

JMX (Java Management Extensions) — это стандартная технология Java для мониторинга и управления приложениями в реальном времени без остановки сервера. Она позволяет наблюдать за внутренним состоянием приложения — счётчиками, статистикой, памятью — прямо во время работы.

MBean (Managed Bean) — это специальный Java-класс который "выставляет" свои данные наружу через JMX. Он состоит из интерфейса (что видно снаружи) и реализации (как это работает внутри). Инструменты мониторинга — JConsole и VisualVM — подключаются к запущенному приложению и показывают данные этих бинов в реальном времени.

## 2. Задание 1 — Наши MBeans

**Что говорить:**

По варианту мы реализовали два MBean-класса встроенных в JSF-приложение лабораторной работы №3.

### MBean №1 — `PointStats`

Считает статистику по точкам которые пользователь ставит на координатной плоскости:

- `TotalPoints` — общее число установленных точек
- `HitPoints` — число точек попавших в область
- `MissPoints` — число промахов
- `HitRate` — процент попаданий

**Ключевая особенность** — реализован механизм уведомлений (Notifications). Когда пользователь совершает 2 промаха подряд, MBean отправляет JMX-уведомление типа `consecutive.misses`. Это реализовано через наследование от `NotificationBroadcasterSupport` — стандартного класса Java для отправки JMX-уведомлений. Подписавшись на уведомления в JConsole во вкладке Notifications можно видеть эти события в реальном времени.

### MBean №2 — `ClickStats`

Считает статистику кликов пользователя по координатной плоскости:

- `TotalClicks` — общее число кликов
- `AverageClickInterval` — средний интервал между кликами в миллисекундах
- `LastClickTime` — время последнего клика (Unix timestamp в мс)

Каждый раз когда пользователь ставит точку — вызывается `recordClick()` который фиксирует время и вычисляет интервал от предыдущего клика.

### Как MBeans интегрированы в приложение

Класс `MBeanRegistrar` помечен аннотациями `@ApplicationScoped` и `@PostConstruct` — это означает что при старте приложения на WildFly он автоматически регистрирует оба MBean в платформенном MBeanServer через `ManagementFactory.getPlatformMBeanServer()`. Имена бинов в JMX дереве: `org.coordinate:type=PointStats` и `org.coordinate:type=ClickStats`. В `PointBean` при каждой проверке точки вызываются методы `recordPoint()` и `recordClick()`.

## 4. Задание 3 — VisualVM

**Что показать и сказать:**

На скриншоте VisualVM видно подключение к удалённому процессу WildFly (`jboss-modules.jar pid 50566`) через Remote соединение. Во вкладке MBeans открыт `ClickStats` и видны графики атрибутов в реальном времени:

- **AverageClickInterval** — график показывает интервал между кликами. Значение 0,0000 в начале — потому что было сделано только 1 клик, интервал ещё не вычислен (нужно минимум 2 клика)
- **LastClickTime** — большое число (~1 780 407 208 130) — это Unix timestamp в миллисекундах, то есть количество миллисекунд с 1 января 1970 года. Так хранится время в Java
- **TotalClicks: 1** — одна точка поставлена

**Про график изменения со временем:** VisualVM автоматически строит график для каждого атрибута. При добавлении новых точек значения на графике меняются — это и есть мониторинг в реальном времени.

**Класс с наибольшим объёмом памяти** — для этого нужно перейти во вкладку Sampler → Memory. Там будет таблица классов отсортированная по занимаемой памяти. Обычно в WildFly наверху оказывается `byte[]` или `char[]` — это внутренние буферы сервера для обработки HTTP запросов и сетевых соединений. Пользовательский класс в котором хранятся эти объекты обычно связан с сетевым слоем WildFly — `io.undertow` (веб-сервер внутри WildFly).

## 5. Задание 4 — Профилирование и проблема производительности

**Что говорить:**

При профилировании через VisualVM Profiler → CPU была выявлена проблема производительности в методе `addResult()` класса `ResultBean`.

**Описание проблемы:**

```java
public void addResult(double x, double y, double r, boolean hit) {
    // ... сохранение в БД
    loadResults(); // ← ПРОБЛЕМА: полная перезагрузка из БД при каждом клике
}
```

После каждого добавления точки выполняется полный SELECT-запрос к базе данных который загружает **все** результаты заново. При небольшом числе точек это незаметно, но при росте числа записей время выполнения будет расти линейно — это проблема производительности O(n).

**Путь устранения:**

Вместо полной перезагрузки достаточно добавить новый результат напрямую в список в памяти:

```java
public void addResult(double x, double y, double r, boolean hit) {
    Result result = new Result(x, y, r, hit, LocalDateTime.now(), executionTime);
    
    // Сохраняем в БД
    // ... persist ...
    
    // Добавляем в список в памяти — БД не трогаем
    results.add(0, new ResultDTO(result)); // ← вместо loadResults()
}
```

Это устраняет лишний запрос к БД и делает операцию O(1) вместо O(n).

**На графике CPU** в VisualVM это проявляется как периодические всплески нагрузки при каждом клике — видны на скриншоте Overview где CPU Usage показывает пики до 30% при казалось бы простой операции добавления точки.
